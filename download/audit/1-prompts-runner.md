# Audit 1 — Agent Prompts + Runtime Loop

Scope: `src/lib/agent/runner-native.ts`, `runner-legacy.ts`, `runner.ts`, `context-manager.ts`, `classifier.ts`, `planner.ts`, `prompt-history.ts`, `followups.ts`, `pattern-memory.ts`, `tool-aliases.ts`, `tool-execution-mode.ts`, `llm-retry.ts`, `pi-ai-model-resolver.ts`, `agent-session-translator.ts`, `src/lib/agent/skills/`, `src/app/api/agent/route.ts`, `src/lib/canvas/store.ts` (send path).
Research-only audit — no source files were modified.

Measured facts used throughout:
- `SYSTEM_PROMPT_TEMPLATE` = **46,116 chars (~11.5K tokens), 630 lines** (`runner-legacy.ts:116–745`).
- Lucide icon catalog injected into the prompt: **194 icons / 14 categories, ~2.0KB** (`src/lib/icons/index.ts:184`, `lucide-registry.generated.ts`).
- Total built system prompt at runtime ≈ 55–65KB (~14–16K tokens) before canvas snapshot: template + skill metadata (7 skills) + active skill body (wireframe body alone ≈ 7.7KB) + palettes + icon catalog + optional design-system pack (≈3.5KB) + file-skills + memory (uncapped).
- Tool surface: ~128 `defineTool` registrations across `tools.ts` (79), `pen-tools.ts` (8), `figma-tools.ts` (10), plugins (~26). Docs variously claim "56", "~70", "88".

## Findings

### P1 — System prompt is a 46KB monolith with six "CRITICAL" sections competing for attention
- **Category:** REWRITE — **Severity:** high
- **Evidence:** `runner-legacy.ts:116–745` (`SYSTEM_PROMPT_TEMPLATE`); "CRITICAL" appears at lines 122 (FIDELITY POLICY), 181 (TEXT LAYER WIDTH RULE), 194 (CONTAINER SIZING), 209 (BATCH CONSTRUCTION), 221 (PARALLEL TOOL EMISSION), 269 (GRADIENT CONTRAST), 620 (ARGUMENT TYPE RULES). Header comment `runner-legacy.ts:95–107`.
- **Finding:** The role statement (2 lines) is immediately buried under ~600 lines of design law, recipes, ramps, icon rules, ontology, and turn-flow protocol. When everything is CRITICAL, nothing is. The genuinely excellent parts (fidelity policy, component recipes, letter-spacing rules, text-width formula, WCAG contract) are interleaved with boilerplate the model rarely needs (full 50–900 hex ramps × 6 colors ≈ 1.6KB, .pen format notes, slot semantics). At ~14–16K tokens this is roughly 10–15% of a 128K window on *every* turn, and it pushes the actual user request + canvas snapshot deeper into the context. Role clarity ("senior product designer operating a Figma-aligned canvas") is good; everything after line 120 dilutes it.
- **Recommendation:** Split into (a) a lean core prompt (role + fidelity policy + turn flow + argument rules, target ≤ 3K tokens) and (b) a separate `DESIGN_COOKBOOK.md` loaded via the existing skill/progressive-disclosure mechanism (the infrastructure already exists — `skills/registry.ts`, `file-skills.ts`). Demote 5 of the 7 "CRITICAL" labels to plain headers. Move the hex ramps into the design-brief sub-agent's prompt (it already owns ramp selection, `subagents/design-brief.ts:81–87`) and reference only "$color.primary ramp" in the main prompt.

### P2 — Critique fix-message instructs the model to call tools that don't exist (deprecated aliases)
- **Category:** UPDATE — **Severity:** high
- **Evidence:** `runner-native.ts:1695` — "You MUST call at least one of: **pen_update_shape, pen_create_shape**, pen_bulk_update_by_filter, …"; `runner-native.ts:1700–1705` — "call **pen_update_shape with { shapeId, … }**". But `runner-native.ts:312–314` filters alias names out of the visible tool set: `const aliasNames = new Set(Object.keys(TOOL_ALIASES)); const filteredTools = allTools.filter((t) => allowedToolNames.has(t.name) && !aliasNames.has(t.name));` and `tool-aliases.ts:30–31` maps `pen_create_shape → pen_create_node`, `pen_update_shape → pen_update_node`. The legacy mirror already uses the canonical names (`runner-legacy.ts:1774`).
- **Finding:** On every critique fix-turn, the model is explicitly ordered to call `pen_update_shape` / `pen_create_shape` — names that are **not registered** in the native session (they were removed from the tool list in the "Agent Performance Package change 6"). The model that obeys gets an unknown-tool error, wastes an iteration, and can trip the stuck detector (3 identical failures → `agent:stuck` → turn aborted). The `{ shapeId, … }` param spelling is also deprecated (`tool-aliases.ts:99`: `shapeId → nodeId`). This directly degrades the highest-leverage quality loop in the product.
- **Recommendation:** In `runner-native.ts:1695–1705` replace `pen_update_shape`→`pen_update_node`, `pen_create_shape`→`pen_create_node`, and `shapeId`→`nodeId`. Add a unit test that asserts every tool name mentioned in the fix-message template exists in `filteredTools`. Longer term, generate the fix-message tool list from the actual visible tool set instead of hardcoding.

### P3 — No cross-turn conversation memory: every turn starts from a blank session
- **Category:** REWRITE — **Severity:** high
- **Evidence:** `runner.ts:361–370` — the route passes only `{ documentId, prompt, canvas, settings, images, selection, canvasDelta, signal }` (no message history); `store.ts:1732–1744` — the client sends only `{ documentId, prompt: text, canvasState, settings, … }`; `runner-native.ts:963–982` — `SessionManager.inMemory(process.cwd())` + fresh `createAgentSession` per `runAgentNative` call; `session.prompt(userMessageWithAttachments …)` (`runner-native.ts:1096`).
- **Finding:** The LLM never sees prior chat turns. Continuity exists only through (a) the canvas snapshot and (b) whatever the agent chose to persist via the memory plugin (`plugins/memory.ts`) or pattern-memory. Consequences: "make it darker" after a screen build works (snapshot shows layers), but any reference to prior *conversation* ("as we discussed", "use the other font you suggested", "yes, do that" after a clarifying question) is unintelligible to the model. The `ask_user_question` plugin answers (`store.ts:934`, `/api/agent/client-responses`) arrive mid-turn, but a follow-up turn after a Q&A exchange loses the question/answer pair entirely unless the model wrote it to memory. For a product pitched as a *collaborative* design agent, this is the single biggest agent-experience gap.
- **Recommendation:** Thread a rolling conversation window into the first user message: last N (e.g. 6) turns as `[CONVERSATION HISTORY (earlier turns)] user: … / assistant: …`, truncated to a token budget, injected *before* the current prompt and *after* the snapshot. The journal already records `agent:user_message` + `agent:turn_final` (text) per turn (`route.ts:194–200, 315–333`) — replay those. Keep it out of the system prompt to preserve prefix caching.

### P4 — Brief-first gate is trivially bypassable and gates names that don't exist
- **Category:** UPDATE — **Severity:** med-high
- **Evidence:** `runner-native.ts:412–418` — `GATED_TOOL_NAMES = ['pen_generate_wireframe', 'pen_create_shape', 'pen_create_node', 'pen_apply_palette', 'pen_set_variable']`. The system prompt's preferred construction tools `pen_create_subtree` (`runner-legacy.ts:209–219` "BATCH CONSTRUCTION RULE … create it with ONE pen_create_subtree call"), `pen_insert_html` (`runner-legacy.ts:672`), `pen_generate_user_flow`, `pen_generate_diagram`, `pen_generate_copy`, `pen_generate_variants` are **not gated**. `pen_create_shape` is an alias that was already filtered out of the tool list (see P2). Legacy mirror has a literal duplicate `'pen_create_node'` twice (`runner-legacy.ts:1346–1348`).
- **Finding:** The "architectural enforcement" (Task 7-e Fix 2) closes the barn door on 4 canonical tools while the prompt actively steers the model to ungated ones. In practice the pre-generated brief (`runner-native.ts:390–409`) usually satisfies the gate before the loop even starts, so the gate only bites when pre-generation fails — exactly the case where the model is most likely to reach for `pen_create_subtree`/`pen_insert_html` and slip through anyway.
- **Recommendation:** Either (a) make the gate exhaustive — gate every mutation tool until `hasGeneratedBrief` (derive the set from `tool-execution-mode.ts`'s non-parallel-safe pen_* names, which is already a close approximation of "mutating tools"), or (b) drop the tool-layer gate entirely and rely on pre-generation + the `[PRE-GENERATED DESIGN BRIEF …]` injection, keeping the gate only as the documented fallback with a correct tool list. Remove the dead `pen_create_shape` entry and the legacy duplicate.

### P5 — The prompt set contradicts itself in at least five places
- **Category:** REWRITE — **Severity:** high
- **Evidence & findings:**
  1. **Vision:** `runner-legacy.ts:149` "You have NO vision — you cannot see images the user pastes and you cannot see your own output" vs `runner-native.ts:804–816` which passes pasted images to `session.prompt(…, { images })` for vision-capable models (and a VLM critic renders the canvas). A vision model is told it is blind; it will ignore or describe-but-not-use attached references.
  2. **Call budget:** `runner-legacy.ts:231` "CALL BUDGET RULE: aim for ≤ 12 tool calls per design request" vs wireframe skill body `skills/registry.ts:183` "Budget ~15-25 tool calls for a proper high-fidelity screen."
  3. **First-screen placement:** `runner-legacy.ts:590–591` "Center of visible area is around (600, 400). Place groups of layers around a focal point." vs `registry.ts:158` "Place the first screen at (100, 100)" vs snapshot placement line `runner-legacy.ts:849` "place the first screen frame around (200, 50)". Three different canonical answers.
  4. **Tool count:** `runner-legacy.ts:118` "…through ~70 typed tools" vs `runner-native.ts:7` "the same 88 ToolDefinitions" vs ~128 actual registrations.
  5. **Double critique:** system prompt TURN FLOW step 8 (`runner-legacy.ts:654`) + "SELF-CRITIQUE IS MANDATORY" (`runner-legacy.ts:616–618`) + wireframe skill step 11 (`registry.ts:125–129`) tell the model to call `pen_self_critique` and fix findings, while the runner *also* runs a mandatory outer critique loop (text critic + VLM critic + validation + fix re-prompt, `runner-native.ts:1450–1832`). The model burns a full context round-trip on `pen_self_critique`, then the runner re-critiques the same canvas — paying the critic cost twice per turn.
- **Recommendation:** Fix 1–4 with text edits (one placement rule — defer to the snapshot's "Next screen placement" line, which is the only dynamic/correct one; one budget number; conditionalize the vision clause on whether images were attached; count tools at build time and interpolate). For 5: when `maxDesignCritiqueIterations > 0`, remove the model-facing `pen_self_critique` mandate from the prompt (or set `pen_self_critique` to parallel-safe-only in the runner's critique phase) so the runner's critics are the single source of critique.

### P6 — The "byte-stable cacheable prefix" is undermined by dynamic sections appended to the system prompt
- **Category:** UPDATE — **Severity:** med-high
- **Evidence:** `runner-native.ts:639–677` — `systemContent = buildSystemPrompt(skillMetadata, skillBody, planSection, canvas, defaultPalette, planFirst, settings?.pack, /* includeSnapshot */ false) + fileSkillsSection + memorySection`. `buildSystemPrompt` interpolates `SKILL_BODY` (varies with classifier result each turn), `PLAN_SECTION` (varies), `PALETTES_LIST` (varies with `defaultPalette` setting); `memorySection` = MEMORY.md + scratchpad + today's + yesterday's logs (`plugins/memory.ts:388–400`), all of which mutate as the agent writes memory mid-session.
- **Finding:** Agent Performance Package change 5 moved the canvas snapshot out of the system prompt precisely so the ~45K-token prefix could hit provider prompt caches across turns — but skill body, plan, and memory still vary turn-to-turn, so cross-turn cache hits only occur when classification, plan-need, and memory content are all unchanged (mostly consecutive identical-style prompts). Within a single turn (multi-iteration) the prefix is stable, which is the case that matters most, but the claimed cross-turn benefit largely evaporates whenever the agent uses its own memory tools — the very behavior the memory plugin encourages.
- **Recommendation:** Keep the system prompt strictly static per document+settings: move `planSection`, `fileSkillsSection`, and `memorySection` into the first user message alongside the snapshot (they're per-turn data anyway). Make `skillBody` selection sticky per session (classify once per document, or re-classify only on category change) so the skill body doesn't flip the prefix between turns. Verify with `cached_tokens` in the usage payload the translator already reports.

### P7 — Context injection is uncapped in three places (snapshot tree, memory, file skills)
- **Category:** UPDATE — **Severity:** medium
- **Evidence:** `runner-legacy.ts:767–839` (`canvasSnapshot` renders **every** shape with no node-count cap; only warnings are capped at 15); `plugins/memory.ts:388–400` (full MEMORY.md + scratchpad + two daily logs, no truncation); `runner-native.ts:646–659` (file-skills section, unbounded). The delta digest (`canvasSnapshotDelta`, `runner-legacy.ts:910–1011`) exists but only activates when the WS service supplies `canvasDelta` (`server.ts:537–566`); the HTTP fallback path always sends the full snapshot.
- **Finding:** A 500-layer canvas (the multi-screen stress tests produced 3–4 screens × 100+ layers) produces a snapshot of 50–150KB ≈ 12–40K tokens injected into the first user message of every turn — on top of the 14–16K-token system prompt and ~30–50KB of tool schemas. There is no degradation strategy for large canvases (no "collapse deep subtrees past depth N", no cap with `pen_get_metadata` pointer, which the delta mode already invented). Memory files grow without bound since nothing prunes them.
- **Recommendation:** Reuse the delta-mode collapsing machinery for the full snapshot: cap rendered lines at ~300 and collapse the remainder to navigation lines with the `pen_get_metadata(nodeId, detail:true)` pointer (the vocabulary already exists in `shape-line.ts`). Cap memory injection (e.g. last 100 lines of MEMORY.md, 30 of scratchpad, 50 of each daily log). Log snapshot token size into `agent:context_update` so regressions are visible.

### P8 — Runner loop: 1,910-line generator with a 15-flag implicit state machine and SDK-internals monkey-patching
- **Category:** RETHINK — **Severity:** medium (high maintenance risk)
- **Evidence:** `runner-native.ts:159–1909` is one `async function*`. Mutable control flags include `didFallback, everSawMessageEnd, everSawTurnEnd, withheldTurnEnd, lastSawActivity, lastSawToolCall, lastSawErrorEvent, lastPromptError, lastStopReason` (+ per-attempt `sawMessageEnd/sawTurnEnd/sawActivity/sawToolCall/sawErrorEvent/promptError` + critique-phase `fixSawActivity/fixSawToolCall/fixError`). `maxIterations` is enforced by probing and overwriting the SDK's internals: `runner-native.ts:1000–1017` (`(session as …).agent`, `'shouldStopAfterTurn' in agentAny`, catch → "loop stays unbounded"). Phases: 2-attempt model-fallback loop → auto-continue (≤2) → critique loop (≤2 × critic-pair + fix-turn) → defensive tail.
- **Finding:** The engineering quality of individual mechanisms is genuinely high (stuck detector with signature tracking `runner-native.ts:849–873`, deferred error surfacing, single authoritative `turn_end`, abort-grace watchdog in the route). But the composition is beyond what a single function can safely hold: every new feature (approval gate, brief gate, plugins, steering, critique) splices another wrapper/flag into the same generator. The `shouldStopAfterTurn` probe does currently work (the SDK assigns the property unconditionally, `pi-agent-core/dist/agent.js:99,125`), but it depends on `AgentSession.agent` staying public and the property being pre-declared — an SDK minor version can silently revert the loop to *unbounded* (the catch block accepts that).
- **Recommendation:** Extract phases into modules with an explicit small state object: `runAttemptLoop()`, `runAutoContinue()`, `runCritiqueLoop()`, `emitTail()`, each owning its flags. Replace the property probe with a supported mechanism (pass `shouldStopAfterTurn` through `createAgentSession` options if the SDK grows it, or wrap at the `customTools` layer by counting executions and returning a terminal error at budget — crude but SDK-stable). Fail loud (log + telemetry event) when the probe fails instead of silently running unbounded.

### P9 — "Legacy" runner is production-dead yet owns all production-critical prompt code
- **Category:** REMOVE/RETHINK — **Severity:** high
- **Evidence:** `runner.ts:49–58` — `runAgent` routes to legacy **only** when `opts.llm` (injectedLlm) is set, which only tests do. Yet `runner-legacy.ts` defines and exports `SYSTEM_PROMPT_TEMPLATE` (line 116), `buildSystemPrompt` (1057), `canvasSnapshot` (767), `canvasSnapshotDelta` (910), `buildSubAgentLLMClient` (1265), `normalizeCanvas` (52), `PROMPT_VERSION` (114) — all imported by the production native runner (`runner-native.ts:87–94`). The legacy loop itself (~700 lines: 1317–1999) duplicates brief-gate, critique loop, escape valve, context management — and has already drifted from native (P2: native's fix-message is *more* stale than legacy's).
- **Finding:** The file layout inverts the architecture: the "production path" imports its brain from the "test path". Every prompt fix must be applied twice or it drifts (P2 is live proof). The dead loop also carries hardcoded `CONTEXT_WINDOW = 128_000` (`runner-legacy.ts:1964`) and a critique loop that can never run its VLM branch.
- **Recommendation:** Move `SYSTEM_PROMPT_TEMPLATE`, `buildSystemPrompt`, `canvasSnapshot(Delta)`, `buildSubAgentLLMClient`, `normalizeCanvas`, palettes/pack builders into a new `src/lib/agent/prompt/` module (e.g. `system-prompt.ts`, `snapshot.ts`, `subagent-llm.ts`). Reduce `runner-legacy.ts` to the test-only loop importing those helpers, or migrate tests to a pi-ai mock Model and delete the legacy loop outright. Keep `PROMPT_VERSION` next to the template it versions.

### P10 — Classifier is keyword-regex-only in production, and tool filtering barely filters
- **Category:** RETHINK — **Severity:** medium
- **Evidence:** `runner-native.ts:269–289` — `classifyIntent({ …, llm: undefined })` with the comment "The keyword pass is reliable enough for production; the LLM fallback was a safety net" (the LLM fallback in `classifier.ts:66–79` therefore never runs on the native path). The always-on floor: `runner-native.ts:297–304` adds `PEN_TOOL_NAMES` (8) + `PEN_TOOL_LEGACY_NAMES` (3) + `FIGMA_TOOL_NAMES` (10) + plugin tools (4 plugins default-on ≈ 10+ tools) on top of `CORE_TOOL_NAMES` (9) and the skill's allowlist (wireframe: ~45). Registry header claims "reduces per-turn tool count from 56 → ~15-20 … well within the 'safe zone' (<25 tools)" (`skills/registry.ts:25–26`).
- **Finding:** In practice every category exposes roughly 40–75 tools (aliases were pruned, but the always-on floor + big wireframe allowlist dominates), so the classifier's main effect is *which skill body text* gets injected, not meaningful tool-count reduction. Meanwhile the keyword pass misroutes plausibly (the registry keywords for wireframe include 'add', 'button', 'card' — an edit like "add a shadow to the card" routes to wireframe, hiding `pen_align_shapes` etc.), and `skillSelectionMode='manual'` already exists as the escape hatch that exposes everything. The classifier also can't see the canvas or selection.
- **Recommendation:** Decide what the classifier is for. If it's prompt-text curation (skill body selection), that's fine — but then stop advertising tool-count reduction and shrink the always-on floor (the 10 Figma hierarchy tools and 8 .pen tools don't need to ride along on every styling turn). If tool filtering is the goal, gate on `pen_*`-always-on being truly core (~10 tools) and re-measure. Wire the LLM fallback via the already-built `subAgentLLM` client (it's OpenAI-shaped — exactly what `classifyIntent` wants) or delete the fallback code.

### P11 — Planner is dead weight on the native path
- **Category:** REMOVE — **Severity:** low-medium
- **Evidence:** `runner-native.ts:551–565` — "we skip the LLM-based planner because we don't have an OpenAI-shaped client … the plan body will be empty unless we wire in a planner LLM later" — `generatePlan({ …, llm: undefined })` → `planner.ts:50–54` returns `null` when `!opts.llm`. So `classification.recommendPlan` in production yields an `agent:plan` event with no steps at best (actually no event at all, since `plan` stays null), yet the prompt's PLAN FIRST section (`runner-legacy.ts:1031–1041`) still makes the model emit a plan text message before its first tool call — one extra round-trip per turn by default (`planFirst ?? true`, `runner-native.ts:165`).
- **Finding:** Two "planning" concepts coexist: (1) the runner-side planner (dead on native), and (2) the prompt-side PLAN FIRST preamble (alive, costs a round trip, and its output isn't persisted anywhere). The pre-generated design brief already serves the "think before drawing" purpose far better (it's structured and injected).
- **Recommendation:** Either wire the planner to `subAgentLLM` (same one-liner as the brief pre-generation) and make PLAN FIRST conditional on it, or delete the planner from the native flow and default `planFirst` off, keeping the brief as the planning artifact. At minimum, stop emitting the `recommendPlan`-triggered dead code path.

### P12 — Prompt history file is misnamed (it's terminal input recall, not LLM history)
- **Category:** UPDATE — **Severity:** low
- **Evidence:** `prompt-history.ts:1–8` — "terminal-style prompt history for the agent chat input. ArrowUp recalls the previous prompt … Persists to localStorage". Consumed only by `AgentPanel.tsx:51,1466–1481`.
- **Finding:** Works as designed (dedupe, cap 50, cursor navigation) but the name collides with the actual LLM-history gap (P3) and confuses audits/contributors. No defect.

### P13 — Followups: fires and is useful, but its suggestions ignore the critique loop's findings
- **Category:** UPDATE — **Severity:** low
- **Evidence:** `followups.ts:27–100` (heuristic, zero-cost, tool-trajectory + canvas-state aware); consumed at `AgentPanel.tsx:2511`. Suggestions like "Add drop shadows to all cards and buttons" / "Fill in realistic copy" duplicate the defects the text/VLM critics just fixed (`runner-native.ts:1603–1610`) — the follow-up engine has no access to critique outcomes.
- **Finding:** Good, cheap feature that demonstrably fires (pure function over last turn's tools + shapes). Two gaps: (a) it doesn't know what the critic already fixed, so it can suggest already-done work; (b) it's wired only to the React panel, not to the WS multi-viewer path (acceptable).
- **Recommendation:** Feed the last `agent:critique` defects (or `allClear` status) into `FollowUpContext` and suppress suggestions already addressed; optionally add a "Critique found X unresolved — run again?" chip when the critique loop exited at budget (`critiqueIteration === maxCritiqueIterations - 1`).

### P14 — Pattern-memory is effectively unreachable in production
- **Category:** REMOVE — **Severity:** medium
- **Evidence:** Tools `pen_search_design_patterns` / `pen_save_design_pattern` / `pen_clear_pattern_memory` / `pen_pattern_stats` are defined in `tools.ts:5374,5426,5458` and listed only in `ALL_TOOL_NAMES` (`skills/registry.ts:753–755`) — the 'multi' fallback. They are **not** in the wireframe/styling/layout allowedTools, so under auto classification they're filtered out (`runner-native.ts:313`); the memory plugin is described as "replaces hand-rolled pattern-memory" (`plugins/index.ts:86`). Nothing in the runner ever calls `storeDesignPattern` automatically (`pattern-memory.ts:72` has no runner-side caller — only the unreachable tool).
- **Finding:** A whole RAG module (JSONL store, Jaccard retrieval, recency/approval boosts, prompt formatter — ~220 lines) plus 4 tool schemas ship in every build but can only execute when classification lands on 'multi' (manual mode or low-confidence fallback). The design-pattern store will therefore stay ~empty, making retrieval moot — the feature has never "fired" in practice.
- **Recommendation:** Either retire pattern-memory (delete tools + module, keep the memory plugin as the one memory system — the codebase's own comment says it replaces this) or auto-store a pattern after each successful design turn (post-critique `allClear`) and surface `retrieveSimilarPatterns` inside the brief sub-agent. Don't keep it in the unreachable middle.

### P15 — Context manager (compaction) is legacy-only; native path disables SDK compaction with no replacement
- **Category:** UPDATE — **Severity:** medium
- **Evidence:** `context-manager.ts` (estimate/shouldCompact/compactToolResults) is imported only by `runner-legacy.ts:1244,1963–1993`. Native: `SettingsManager.inMemory({ compaction: { enabled: false } })` with the comment "our context-manager.ts already handles truncation" (`runner-native.ts:973–979`) — but context-manager never runs on the native path, so nothing compacts. The mega-compact plugin that would replace it is `defaultEnabled: false` (`plugins/index.ts:96`).
- **Finding:** On the native path, a long critique-heavy turn (main loop + ≤2 fix-turns + auto-continue, each re-sending the full prefix) relies solely on the model's context window; the `agent:context_update` events the UI renders come from the translator's usage math, not from any active compaction. The stale comment claims a safety net that doesn't exist.
- **Recommendation:** Either enable the SDK's native compaction and translate `compaction_start/end` into a UI state (the TODO already says "Re-enable when we're ready"), or enable mega-compact by default for long turns, or run a context check before each critique fix re-prompt (the fix re-prompt is where context blow-ups concentrate). Fix the misleading comment.

### P16 — Good bones worth keeping (positive findings)
- **Category:** UPDATE (keep/strengthen) — **Severity:** n/a
- **Evidence & findings:**
  - **Delta snapshot design** (`canvasSnapshotDelta`, `runner-legacy.ts:896–1011`): changed nodes full-detail, unchanged subtrees collapsed with an on-demand hydration pointer, globals always present — this is the right architecture (tldraw getChangesSince + Linear late-enrichment). Extend it per P7.
  - **Deterministic tool ordering + prompt-cache env** (`runner-native.ts:528–537`, `689`): sorting tools alphabetically after all wrappers and setting `PI_CACHE_RETENTION=long` — correct and verified.
  - **Order-preserving batch execution** (`tool-execution-mode.ts`): sequential for mutations, parallel for reads — sound and well-documented.
  - **Stuck detector** (`runner-native.ts:849–873,1154–1183`): signature-based, bounded, honest `agent:stuck` event — better than most production agents.
  - **Anti-pattern coverage in the prompt**: mid-word wrapping (text-width formula), container overflow, invisible gradients (30° hue separation), emoji icons, wireframe-vs-hifi, brand-string fidelity, "next screen placement" — these are unusually concrete and clearly born from real failures.
  - **Selection context + pack reminder riding the user message** (`runner-native.ts:741–752`): cheap, well-placed nudges.
  - **Error taxonomy + retry ladder** (`llm-retry.ts`, `agent-error.ts`) and the route's abort-grace watchdog (`route.ts:215–274`): production-grade.

### P17 — Edit-turn guidance is thin relative to create-turn guidance
- **Category:** REWRITE — **Severity:** medium
- **Evidence:** The system prompt's only edit-specific rules are `runner-legacy.ts:592` ("ALWAYS call pen_get_metadata before updating/deleting existing layers") and the READ LADDER (690–700). The delta snapshot header teaches on-demand hydration (`runner-legacy.ts:1006–1010`), but the system prompt never mentions delta mode, never explains how to resolve a name like "the hero" to a node id (pen_find_nodes exists), and TURN FLOW (`runner-legacy.ts:633–660`) describes only the create path.
- **Finding:** The product's own usage pattern (multi-screen stress tests: turn 2 = "now create the dashboard screen", turn 3 = "make the cards darker") is edit-heavy, yet the prompt's guidance is ~95% create-oriented. The classifier routes edits into skills (layout/styling) whose bodies do cover edit tools, but the *system* prompt gives no edit workflow (find → verify → patch → re-verify) and no "reuse the existing $color.* variables; don't redefine the palette" rule on edit turns — a common source of drift within a document.
- **Recommendation:** Add a short EDIT TURNS section: "When the canvas is non-empty and the request references existing content: (1) read the snapshot/delta; (2) resolve targets with pen_find_nodes / pen_get_metadata; (3) mutate with pen_update_node / pen_bulk_update_by_filter; (4) REUSE the document's existing $variables — never redefine $color.* on an edit turn; (5) verify with pen_get_metadata." Gate it textually on "canvas already has layers".

### P18 — `isDesignRequest` / `isAmbiguousCreation` / `QUESTIONISH_PROMPT` heuristics are triplicated and only English-aware
- **Category:** UPDATE — **Severity:** low-medium
- **Evidence:** `runner-native.ts:332–336` (`isDesignRequest` regex), `:357–367` (`isAmbiguousCreation` — pinned-direction regex includes brand names like stripe/linear/vercel), `:384–388` (`QUESTIONISH_PROMPT`); wireframe-request regex duplicated in the critique loop (`:1523–1526`) and legacy (`:1697–1698`); skill keywords (`registry.ts:257–271`) encode a fourth overlapping vocabulary.
- **Finding:** Four parallel keyword vocabularies decide gate/brief/critique/variant behavior. They disagree at the edges (e.g. "make a quick mockup of the pricing page" → ambiguous-creation says pinned? no; wireframe regex fires; brief gate skipped; critique loop skipped — probably intended, but only by luck of regex interaction). Non-English prompts fall through to defaults everywhere.
- **Recommendation:** Centralize intent micro-signals (design-request, wireframe-request, ambiguous-creation, questionish) into one module (`intent-signals.ts`) with a single test suite covering the interactions; have classifier, runner gates, and critique loop consume it.
