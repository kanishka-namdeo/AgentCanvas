## Findings

### S1 — The mandatory critique loop actuates fixes through tools that don't exist
- **Category:** REWRITE · **Severity:** High
- **Evidence:** runner-native.ts:1688–1708 (fixMessage); runner-native.ts:312–314 (alias entries filtered OUT of the native registry — "a model that hallucinates a deprecated name gets a standard unknown-tool error"); registry.test.ts:119–124 (legacy spellings deliberately not registered).
- **Finding:** The critique loop's whole purpose is to make the model fix defects. Its fix-message says "You MUST call at least one of: pen_update_shape, pen_create_shape, pen_bulk_update_by_filter, pen_set_shadow, pen_set_gradient_fill, pen_apply_palette" — **2 of the 6 mandated tools are unregistered**, and the per-defect recipes that follow name `pen_update_shape` with a `{shapeId, fontWeight}` contract **five more times** (fontWeight, letterSpacing, textAlign, autoLayout, resize). The real path is `pen_update_node {nodeId, changes:{...}}`. So the fix-turn's most-specific instructions are a map to "Tool not found" errors. This deepens audit-2 T2 from "risk on fix-turns" to: *the loop's core actuation text is poisoned at every specific instruction*. The noOpFixAttempts counter (1487, 1800–1809) then punishes the model for not calling tools it was misdirected about.
- **Recommendation:** Rewrite the fix-message recipes against the registered surface (`pen_update_node` with `changes`, `pen_bulk_update_by_filter` filter+changes), and add a unit test that asserts every tool name string in the fix-message ∩ registered tool names (string-level guard, same spirit as registry.test.ts).

### S2 — The VLM critic never sees the real rendered canvas on the mandatory path
- **Category:** UPDATE · **Severity:** High
- **Evidence:** design-critic-vlm.ts:133–154 (`hasSink()` gate → client screenshot round-trip; else resvg fallback); runner-native.ts:1229 (`restoreEventSink()` in the attempt loop's finally) vs 1555–1591 (critics dispatched *after* the finally, before the fix-turn re-installs a sink at 1731).
- **Finding:** The event sink is un-installed the moment the main loop ends. When the critique loop's VLM critic runs, `hasSink()` is false on **every** critic invocation (iteration 0 and post-fix iterations — the fix-turn's sink is itself restored at 1781). So the "ground-truth client screenshot first" design (spec §5.4 / M2-c, and audit 2-e's #1 best practice: *vision model sees the actual rendered image*) silently degrades to the server-side resvg approximation — the exact renderer whose fidelity gaps audit 4 documented (0.62×fontSize text estimate that ignores wrapping, 100×100 fit_content placeholders, unrendered masks/blend modes). The critic's `screenshotSource` telemetry will read `'server'` 100% of the time in the loop. The only paths where the client screenshot works are mid-turn tool calls — and the one tool that would use it (`pen_visual_critique`) is unreachable (audit 2 T1).
- **Recommendation:** Install a sink for the critique phase (or capture the screenshot *before* the attempt loop ends / pass a `getScreenshot` callback that uses the still-live socket). At minimum, surface `screenshotSource: 'server'` in the `agent:critique` event so the "VLM 7/10" chip doesn't overclaim.

### S3 — Four overlapping critique paths; the runner loop makes two of them redundant
- **Category:** RETHINK · **Severity:** High
- **Evidence:** (1) system-prompt critique mandates (audit 1 P3 "double critique mandate"); (2) wireframe skill body step 11: "SELF-CRITIQUE (MANDATORY for high-fidelity work): … call pen_self_critique" (registry.ts:125–129); (3) runner mandatory loop: text + VLM critics, `maxDesignCritiqueIterations` default 2, critics run once per iteration → **2 text-critic + 2 VLM-critic calls minimum per design turn even when output is clean** (runner-native.ts:1495, 1555–1591; settings/types.ts:319); (4) default-on `subagents` plugin exposing `subagent_reviewer` whose promptGuidelines even say "Re-run subagent_reviewer after fixes to verify the score improved" (subagents.ts:193–198).
- **Finding:** On a standard wireframe-classified turn the model is instructed to run the text critic mid-turn (skill body), and then the runner runs the *same design-critic sub-agent with a nearly identical prompt* again after the turn — plus the VLM critic, twice. That's a guaranteed duplicate text critique on every design turn (~10–15s + tokens each) and a 3rd/4th redundancy if the model also finds `subagent_reviewer`. The runner loop is the right enforcement point (audit 2-e: mandatory critique = highest-leverage); the agent-invoked variants are now legacy plumbing that add cost and selection noise.
- **Recommendation:** Keep the runner loop as the single critique authority. Remove the "MANDATORY self-critique" step from the wireframe body (keep one line: "the system runs an automatic critic pass; address its findings"), default the `subagents` plugin OFF, and either delete `pen_self_critique`/`subagent_reviewer` or re-skin them as "critique now" triggers of the runner's critic (same dispatch, one implementation).

### S4 — `subagents` plugin: default-on, degraded critic clone + trap tool; only its side-door is valuable
- **Category:** REMOVE · **Severity:** Medium (High for multi-screen correctness)
- **Evidence:** subagents.ts:280–313 (`subagent_worker` placeholder returns success); subagents.ts:31–65 (REVIEWER prompt = design-critic's prompt minus wireframe-detection examples, fidelity gate examples, and the 1–10 scoring guide); subagents.ts:137–167 (`serializeCanvasForSubagent` — no `priorShapeIds` scoping, no fidelity summary, no wireframe heuristic, unlike design-critic.ts:204–298); plugins/index.ts:124–130 (defaultEnabled: true).
- **Finding:** Beyond T8's duplication finding, the reviewer clone is a **regression vector**: the design-critic's prior-content scoping exists because the critic "used to review the whole canvas and flag the user's earlier screens as defects, which the fix-turn then 'resolved' by deleting them" (design-critic.ts:121–126). `subagent_reviewer` reintroduces exactly that unscoped behavior — if the model calls it on a multi-screen canvas, prior screens get flagged as defects, and the runner's prior-content guard (which is only active during *its own* fix-turns) won't be armed for the model's self-directed "fixes". The oracle is benign but generic. The module's real value is `getActiveLLM()` (variant-generator.ts:309, and the brief/critic fallbacks) — infrastructure masquerading as a plugin.
- **Recommendation:** Extract `setActiveLLM/getActiveLLM` into a shared module (e.g. `llm-slots.ts`), delete the plugin or default it off (aligns with T8's recommendation), and if the reviewer survives, make it call `dispatchDesignCriticSubAgent` with `priorShapeIds` from the runner.

### S5 — `subagent_reviewer` reads a stale (turn-start) canvas snapshot
- **Category:** UPDATE · **Severity:** Medium
- **Evidence:** runner-native.ts:1079–1080 (`setSubagentActiveCanvas(canvas)` — once per attempt, before the turn runs); runner-native.ts:203–211 (`ctx.applyPatch` *reassigns* the `canvas` closure variable on every patch); subagents.ts:210, 318–322 (tool reads module-level `activeCanvas`).
- **Finding:** The canvas slot is captured before the model creates anything, and `applyPatchToCanvas` returns a new document object — the module slot never sees the turn's output. If the model calls `subagent_reviewer` mid-turn after generating a screen, the reviewer serializes the **pre-turn** canvas: on a fresh document that's literally `(empty canvas)`, producing a critique of nothing (or, worse, of the user's prior screens only). The slot is only refreshed at fix-turn start (1738), long after the tool's most likely use window. (Contrast: `pen_*` tools read through the `ctx` closure and always see live state.)
- **Recommendation:** If the plugin stays, pass a getter: `setSubagentActiveCanvasProvider(() => canvas)` or reuse `ctx.getDocument` wiring. If S4 removes the plugin, this is moot — but the pattern (module slot vs closure) should be documented for future sub-agent tools.

### S6 — Blocking plugin tools vs the 120s stream watchdog; `goal_interview` is outright broken
- **Category:** UPDATE · **Severity:** Medium (High for the goal plugin)
- **Evidence:** ask-user-question.ts:35 (`ASK_TIMEOUT_MS = 5 min`), 149–155 (silent block, no events/updates while waiting); approval-gate.ts:89 (`APPROVAL_TIMEOUT_MS = 5 min`, auto-DENY); route.ts:215 (`WATCHDOG_MS = 120_000`), 247–274 (abort + "stream stalled" error on 2 min of wire silence), 429 (`lastActivity` only advances on yielded events); goal-list-loop-audit.ts:118–133 (poll of `getPendingQuestions()` for an id **never registered** there).
- **Finding:** Three wiring bugs in one class: (a) a user who takes >2 minutes to answer an `ask_user_question` dialog (or an approval prompt) gets the run killed as "stalled" — the tool's 5-min timeout is unreachable through the wire; the model never receives the answers even if the user submits at minute 3 (the run is dead; the pending entry resolves into a void). (b) `goal_interview` emits the question dialog but never registers in `pendingQuestions`, so its 100ms poll immediately sees the id absent and "resolves" with `[['(interview completed)']]` — the goal is recorded with criteria `"(no answer)"` while the user stares at a dialog whose submission is discarded by `resolveAskUserQuestion`'s no-op path. (c) Both 5-min timeouts advertise UX the transport cannot honor.
- **Recommendation:** Emit a keep-alive (tool_update / no-op event) from blocking tools, or exempt interactive-blocked runs from the watchdog (a shared "awaiting user" state flag). Fix `goal_interview` by registering a real pending entry (reuse `resolveAskUserQuestion`'s map with a wrapper) or by awaiting the same promise the ask-user tool uses. Until fixed, remove goal-list from the Settings catalog.

### S7 — Default-off plugins are shippable-looking stubs that lie to the model
- **Category:** REMOVE · **Severity:** Medium
- **Evidence:** mega-compact.ts:87–91 ("The runner subscribes to a 'compact_now' signal — see runner-native.ts" — no such subscription exists; `recordCompaction` (48) has zero callers, so `compact_search`/`compact_stats` query an index that is always empty; SDK compaction is explicitly disabled, runner-native.ts:979); background-tasks.ts:129–135 ("The frontend's AgentPanel subscribes … and POSTs to /api/agent/background/<id>/run" — no such route exists; only `GET /api/agent/background/[id]`; `registerTaskComplete` (86) has zero callers); mcp-adapter.ts:189–197 & 210–220 (`mcp_call_tool` / `mcp_read_resource` return "dispatched … result will be returned via the MCP API route" — it never returns; the model is left holding a fake receipt).
- **Finding:** These four plugins are toggleable in Settings → Plugins and present as capabilities ("Connect to MCP servers (Figma, GitHub, Notion…)", "Durable background task execution"). A user who enables them arms the agent with tools that consume a call, report progress/success, and never deliver the work — `background_enqueue` is the worst: the model is told to "poll background_status periodically", which against a permanently-`pending` task is a polite infinite loop. This is the `subagent_worker` trap (T8) generalized to three more modules.
- **Recommendation:** Remove or clearly gate behind an "experimental/not implemented" flag in the manifest (surfaced in the Settings UI). For mcp-adapter, either wire `mcp_call_tool` to the actual MCP SDK route call (await the result and return it) or keep only `mcp_list_servers`. For mega-compact, delete until compaction is real. For background-tasks, delete until an executor exists.

### S8 — Legacy file-skills inject deprecated tool names into every system prompt
- **Category:** UPDATE · **Severity:** Medium
- **Evidence:** `.pi/skills/design-system.md` Guidelines 3–6 (`pen_update_tokens`, `pen_set_variable` "for theme-conditional values", `pen_bind_shape_to_token`, `pen_apply_token`, `pen_list_tokens`); `.pi/skills/wireframe-generator.md` Guidelines 3 ("call `pen_list_shapes`"), Tools list (`pen_update_shape`); `.pi/skills/design-audit.md` (`pen_list_shapes`, `pen_find_shapes`); injected unconditionally via file-skills.ts:288–305 → runner-native.ts:646–659; aliases filtered from the registry at runner-native.ts:312–314 (registry.test.ts:119–124 codifies their absence).
- **Finding:** Up to ~20 numbered guidelines ride the system prompt on every turn, and the three legacy files teach **7 deprecated spellings** that all produce "Tool not found" on the native path. Combined with S1, the prompt actively coaches the model into exactly the failure mode the alias-removal comment says it should "self-correct" from — burning 1–2 iterations of the ≤12-call budget on styling/wireframe/inspect turns. The files also duplicate (and predate) the registry skills' guidance (wireframe-generator.md's "keep tool calls under 15" vs the system prompt's ≤12 vs the skill body's 15–25 — three budgets, audit 1 P3's contradiction family grows).
- **Recommendation:** Rewrite the three legacy files to canonical names (or delete them — the registry skills supersede them), and add a loader-level lint: reject/skip any guideline line matching `TOOL_ALIASES` keys or containing a `pen_\w+` token not in `ALL_TOOL_NAMES`. Make injection conditional on the active skill matching the file-skill's domain while you're there.

### S9 — Skill routing is one-skill-deep: secondary categories never widen the tool set; classifier fallback unwired
- **Category:** UPDATE · **Severity:** Medium
- **Evidence:** classifier.ts:228–230 (`secondaryCategories` computed for every multi-match prompt) vs runner-native.ts:297–304 (`allowedToolNames` = primary category only + always-on unions; `secondaryCategories` consumed solely for the web-research dispatch at 589–591); runner-native.ts:268–289 (LLM classifier fallback never constructed: `llm: undefined`); layout allowlist (registry.ts:330–359) contains zero styling tools.
- **Finding:** The classifier *knows* "align these cards then make them blue" spans layout+styling (both score), but only the primary's tools become visible — the model must do styling work through the generic `pen_update_node {changes}` instead of `pen_apply_palette`/`pen_set_shadow`. The types.ts comment (types.ts:83–85: "a prompt that asks to 'research then design' needs both") documents an intent the wiring never implemented beyond web_research. Meanwhile, the `multi` fallback (zero keyword matches) throws the model into 110+ tools with **no Level-2 body at all** — the least-guided configuration gets the most surface. And because the LLM classifier is unwired, routing quality is entirely at the mercy of the keyword lists (which have already needed two live-fire patches: Fix 4a/4b/4c).
- **Recommendation:** Union the secondary categories' allowlists into `allowedToolNames` (cheap, one line — the sets exist). Wire the classifier's LLM fallback using `subAgentLLM` (already built at 245–253). For `multi`, inject a short generic body ("all tools visible; prefer pen_create_subtree; ≤12 calls") instead of none.

### S10 — Progressive disclosure works mechanically, but the wireframe body contradicts the system prompt and re-teaches the old workflow
- **Category:** UPDATE · **Severity:** Medium
- **Evidence:** registry.ts:63–184 (body: "Budget ~15-25 tool calls", step 1 "call pen_generate_wireframe FIRST", step 3 "Define the semantic color tokens via pen_set_variable", steps 5–9 one-tool-at-a-time elevation) vs runner-legacy.ts:231–235 (CALL BUDGET ≤12; "pen_create_subtree instead of N calls"), vs the pre-generated brief making tokens/palette the brief's job (perf change 9), and vs the design-brief gate messaging.

Latency answer to the brief's question: skills currently **add** both tokens (~1–2K body) and latency (playbook lengthens turns) relative to the terse system-prompt rules; their genuine value is arg-formatting rules + completion criteria, which measurably reduce failure loops.

### S11 — Web-research and brief sub-agents serialize before the main loop; critic phase is silent in the UI
- **Category:** UPDATE · **Severity:** Low/Medium
- **Evidence:** runner-native.ts:390–409 (brief pre-generation awaited before session creation, 40s worst case) and 593–634 (web-research awaited before the first prompt; up to 6 LLM iterations ≈ 1–3 min); critique loop 1555–1630 emits **nothing** between the main turn's end and the `agent:critique` event (no `agent:subagent_dispatch` for the critics — the SubAgentsCard never appears for them); fixIntro text (1646) only appears after both critics return.
- **Finding:** Cost/latency structure: on a "research then design" turn the user waits research (1–3 min) + brief (up to 40s) before the model's first token. The research dispatch event does show a card (good), but the brief is silent, and the ~15–40s critic phase (two parallel sub-agents) is a dead-air window on every design turn — the run looks frozen precisely when users are most likely to resend or Stop. The fixIntro + CritiqueRow pattern is right; it's just one event too late.
- **Recommendation:** Race brief pre-generation against session creation (they're independent); emit `agent:subagent_dispatch {subAgentType: 'design_critic' | 'design_critic_vlm'}` around the Promise.all — the UI card already exists and costs nothing. Optionally start research concurrently with the main session's *first* iteration and steer it in (session.steer exists).

### S12 — Process-global mutable slots: cross-run clobbering, unbounded session maps, cross-user memory
- **Category:** UPDATE · **Severity:** Medium (deployment) / Low (current single-user sandbox)
- **Evidence:** event-bus.ts:18 (single `currentSink` — "the runner is single-threaded per request" is asserted, not enforced); todo.ts:48 / goal-list-loop-audit.ts:42 / background-tasks.ts (per-session Maps, never evicted); subagents.ts:171, 318 (single `activeLLM`/`activeCanvas`); memory.ts:30–34 (`~/.pi/agent/memory` — one store for the whole server); canvas/server.ts:70, 526 (`activeRuns` keyed by documentId — concurrent runs on *different* documents are supported).
- **Finding:** Two simultaneous turns on two documents will clobber each other's event sink (run A's plugin events land in run B's stream — ask-user answers, todo updates), each other's `activeLLM`/`activeCanvas`, and the todo `activeSessionId` (the second run's `setTodoActiveSession` wins mid-flight of the first). Todo lists accumulate per documentId forever. The memory plugin stores every user's "durable preferences" in one global MEMORY.md injected into *everyone's* system prompt — a privacy/correctness leak in any multi-user deployment, and unbounded prompt growth as MEMORY.md accumulates (no size cap on the injected section; only today+yesterday dailies are included, but MEMORY.md has no pruning).
- **Recommendation:** Thread a per-run context object through the plugin tool factory instead of module slots (the runner already builds `customTools` per run — plugins could be factories too). Key the event sink by documentId like `activeRuns`. Cap the injected memory section (e.g. last N lines) and namespace MEMORY.md by document/user.

## Top 8 prioritized changes

1. **Fix the critique fix-message's tool contract (S1)** — swap `pen_update_shape`/`pen_create_shape` + `{shapeId, …}` recipes for `pen_update_node {nodeId, changes:{…}}` / `pen_bulk_update_by_filter`; add a string-level test that every tool name in the fix-message is registered. They are Settings-toggleable traps in the same class as `subagent_worker`.

8. **De-globalize the plugin runtime (S12)** — per-run context instead of module slots (sink, activeLLM/activeCanvas, session ids), keyed event routing, and per-document (or capped) memory injection. Unblocks correct multi-document/multi-user operation and stops unbounded map growth.
